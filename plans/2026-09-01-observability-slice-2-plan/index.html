    mauto Observability — Slice 2 Implementation Plan (daemon instrumentation)¶

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Make the session daemon observable — per-primitive call latency, timeout counts and mobile-mcp error rates from the one call seam every verb passes through, plus the daemon's lifecycle (start, lock conflict, connect failure, listen failure, stop-with-reason, crash) and the existing undeliverable-reply seam — all correlated by a new session_id that names one daemon lifetime.

    Architecture: The daemon does not call record() directly. bin/mauto-session-daemon.js builds one bound recorder at process start (src/observe/daemon-recorder.js) and injects it into startDaemon as an observe(fields) function, alongside the existing createCall / scheduleTimeout / execFile injection seams. startDaemon's default observe is a no-op, so the ~40 existing in-process daemon tests are untouched and the new instrumentation is tested by injecting a collector. Daemon events land in their own NDJSON file, mobile-automator/.logs/daemon.ndjson, separate from the CLI's mauto.ndjson. session_id is generated by the daemon process and written into the session.json handle that already exists, so verbs read it from a file rather than paying a socket round-trip.

    Tech Stack: Node.js (CommonJS), Commander, Jest. No new dependencies — this is a hard constraint, not a preference.

    Spec: docs/plans/2026-08-31-observability-design.md (slice 2 in its slice ladder). Slice 1's plan, whose conventions this one continues: docs/plans/2026-08-31-observability-plan.md.

    Global Constraints¶

    • No new dependencies. Cold start is ~112ms and one scenario is dozens of process spawns. Nothing may be added to package.json dependencies.
    • stdout belongs exclusively to the verb's own output. No sink may ever write to stdout. This applies to the daemon too: it holds no stdout of its own worth protecting, but startDaemon also runs in-process inside the unit suite, where a stray stdout write would corrupt jest's reporter.
    • The recorder must never throw and never propagate. record() already guarantees this; every new call site inherits it. An observability failure must never take the daemon down, and must never turn a successful device call into a failed one.
    • Fields are allowlisted, never denylisted. Any new field must get an EVENT_FIELDS entry in src/observe/event.js with a sends flag and a why, or makeEvent silently drops it and tests/lint/telemetry-redaction.test.js fails the build.
    • A sends: true justification must be enforced, not asserted. event.js already sets this bar for verb ("cli.js takes it from commander's resolved command, never from argv"). Slice 2 adds two fields with the same obligation: session_id (enforced by its generator) and tool (enforced against a closed set).
    • One rotation policy. src/util/log-rotate.js (MAX_LOG_BYTES, rotateIfLarge) is it. Do not fork it, do not add a second constant, do not add a second generation.
    • Raw daemon stdio stays at mobile-automator/.session/daemon.log (PR #176). Slice 2 does not re-plumb daemon stdio, does not touch session-log.js, and does not touch spawnDaemon's openLog seam. It adds structured events alongside the raw capture.
    • Slice 2 wires no network transport. telemetryPayload() gains new eligible fields; nothing sends them anywhere until slice 5.
    • CI version gate: this touches src/ and bin/, so package.json version must be bumped to a value not yet in git tag. main is at 0.24.0, slice 1 took the branch to 0.25.0-rc.0, so slice 2's target is 0.25.0-rc.1.
    • No MAUTO_OBSERVE gate in this slice, deliberately. The design says "slices 2–5 gate their user-visible verbs behind MAUTO_OBSERVE=1". Slice 2 adds no verb and no flag. Its two surfaces are (a) structured log lines, which slice 1 already ships ungated, and (b) one additive session_id field on mauto session status. Gating a log line produces a partial state that is harder to reason about, not easier, and gating the status field would leave session_id in the handle but invisible — the exact half-built state the gate exists to prevent. The gate clause applies vacuously here; slices 4 and 5, which do add verbs, must honour it.
    • Platform-agnostic: never emit resource-id or OS-specific element IDs in any artifact.

    The long-lived-process analysis¶

    record() was built for a process that records once and exits immediately. The daemon is detached and lives for minutes to hours, serving one device call after another. Everything in the task list below follows from working out what that actually changes — so the reasoning is stated once, here, rather than re-derived in eight task comments.

    What changes¶

    1. projectRoot cannot come from process.cwd(). record() defaults projectRoot to process.cwd(). For a one-shot verb that is correct by construction. The daemon inherits its cwd from whichever verb happened to spawn it (session-spawn.js passes no cwd) and then outlives that verb — the user can cd away, delete the directory, or spawn the daemon from a subdirectory of the project. The daemon does, however, have an authoritative project root: MAUTO_SESSION_PROJECT_ROOT. So the daemon's recorder is bound to projectRoot once, at construction, and no daemon call site ever relies on the record() default.

    2. Level resolution moves from per-event to per-process. record() calls resolveLevels(env) on every call when no sinks are injected. For the CLI that is once per process. For the daemon it would be once per device call — re-reading an environment that cannot change: nothing can export a variable into a running detached process. So makeDaemonRecorder resolves levels and builds its sink list once. Consequence worth documenting: MAUTO_LOG_LEVEL and MAUTO_LOG_DIR are captured from whichever verb spawned the daemon and are pinned for the daemon's whole lifetime. A later MAUTO_LOG_LEVEL=debug mauto tap gets debug CLI events and whatever the daemon was born with. mauto session end then re-running is the way to change it. This is a property of daemon spawn, not of the recorder, and it is the same for every other spawn-time env var already.

    3. Level choice inverts, and this is the first real warn/error in the codebase. src/cli.js finish() records verb.end at info unconditionally, and the comment there says why: warn would clear the default stderr threshold and print a line on every failed verb, restating in a worse format the envelope the CLI just wrote to stdout. stderr is a human's terminal and stays quiet.

    For the daemon that calculus is exactly inverted. Since PR #176 the daemon's stderr is mobile-automator/.session/daemon.log — a file nobody reads unless something broke, sitting next to the adb/simctl output that explains the failure. A warn line there costs a human nothing and lands precisely where a human debugging a dead daemon is already looking. PR #178 recorded the consequence that nothing currently reaches stderr at the default warn threshold; daemon lifecycle failures are the natural first genuine warn/error events, and that is a deliberate choice, not an accident of routing. The levels chosen:

    Event Level Why
    daemon.start info Normal. File-only at the default threshold.
    daemon.stop info Normal, including the idle reap.
    daemon.lock_conflict warn A spawn race loser is doing the right thing, but a workspace where this repeats means two agents are fighting. Not an error.
    daemon.start_failure error The lock could not be taken for a reason other than a race (EACCES, EROFS, ENOSPC). Invisible death.
    daemon.connect_failure error mobile-mcp never came up. This is #156's core symptom.
    daemon.listen_failure error Bound nothing; every verb silently falls back to one-shot.
    daemon.crash error uncaughtException / unhandledRejection.
    daemon.undeliverable warn The device already acted and the reply is lost; the client will hang to its own 30s timeout. Bad, recoverable.
    call.start debug Off by default. See point 5.
    call.end (ok) info The latency/throughput record.
    call.end (failed) warn A failed device call is exactly what the human reading daemon.log wants marked.

    4. Which file daemon events go in — a new one, mobile-automator/.logs/daemon.ndjson. The alternative was appending to the CLI's mauto.ndjson, and the deciding factor is rotation, not readability.

    The append itself would have been fine. appendFileSync opens with O_APPEND and closes per call, so concurrent writers do not share an offset and a ~300-byte line is written by a single write(2) on any local filesystem. Two processes appending short lines interleave cleanly.

    Rotation does not. rotateIfLarge is statSync then renameSync, and both the daemon and a one-shot verb would run it against the same path. Two concurrent rotations mean the second rename clobbers the .1 the first just created, destroying a whole generation of an already-single-generation log; a rotation that lands between another writer's open and its write silently deposits that line in the rotated file. Neither corrupts anything, but both lose exactly the records you went looking for. Giving the one long-lived writer its own file makes its rotation a single-writer operation and removes the interaction entirely.

    Two supporting reasons. Volume: a 40-step scenario is ~40 CLI verb.end lines against 40+ daemon call.end lines, so a shared 1 MiB file would rotate the CLI's history out roughly twice as fast. Precedent: .session/daemon.log is already a daemon-owned file distinct from the CLI's diagnostics — two writers, two files is the shape this codebase already chose.

    The cost is one extra file to read. It is small: both files are NDJSON with an ISO ts and a src field, so cat mobile-automator/.logs/*.ndjson | sort is a merged timeline, and the Task 9 TROUBLESHOOTING entry documents exactly that.

    Residual concurrency, stated honestly: a spawn race means a lock loser also runs bin/mauto-session-daemon.js and writes daemon.lock_conflict to the same daemon.ndjson as the winner. That is a handful of ~200-byte appends in a window of milliseconds, and the worst case is one lost rotation generation of a bounded log. rotateIfLarge already swallows the ENOENT a losing rename produces. Accepted, not overlooked.

    5. appendFileSync per event stays — buffering would break the feature. At the default level the daemon writes one file line per device call (call.start is debug; call.end is info). A device call is an adb/simctl round trip: 40ms for a tap, seconds for an element dump, up to the 25s DAEMON_CALL_TIMEOUT_MS. An open+write+close of ~300 bytes to a local filesystem is tens of microseconds. Even at an unrealistic 25 calls/second that is well under 0.1% of one core, and against a ≥40ms round trip the per-call overhead is under a tenth of a percent. There is no cost to buy back.

    And buffering would cost the feature its point. The daemon's most valuable events are its last ones — the uncaughtException, the call.start with no matching call.end, the connect_failure. Those are precisely the moments where a buffer is not flushed: process.exit(1) from the crash guard, a SIGKILL, an idle reap that races teardown. Synchronous append is a durability property here, not an oversight. Task 6 pins the one-append-per-call claim with a test so the cost argument stays true.

    6. No held file descriptor, despite the process being long-lived. Holding one open fd is the obvious optimisation for a long-lived writer and it is wrong here. An open fd pins the inode: after rotateIfLarge renames the file, the daemon would keep writing into daemon.ndjson.1 while the live log sat empty — the classic copytruncate failure, invisible until someone notices the wrong file growing. It also adds process-lifetime state that must be released on stop(), on both crash guards and on both signal paths: four more teardown paths to get right, to save tens of microseconds per call.

    Contrast with openDaemonLog (#176), which does hold an fd. That is not an inconsistency: that fd exists to be handed to child_process.spawn as the child's stdio, so there is no open-per-write option available. Different constraint, different answer.

    What deliberately does not change¶

    src/observe/recorder.js, src/observe/settings.js, src/observe/sinks/stderr.js and src/util/log-rotate.js are untouched. src/observe/sinks/file.js gains one optional logPath argument and nothing else. The daemon reuses the same event model, the same level semantics, the same redaction catalog and the same rotation policy as the CLI — everything that changes is binding (which root, which file, which levels, resolved when), not mechanism.

    Task 1: Vocabulary — new catalog fields and the mobile-mcp tool allowlist¶

    Written first because every later task uses these names, and because a field without a catalog entry is silently dropped by makeEvent rather than failing loudly at the call site.

    tool is the interesting one. The design wants "per-primitive call latency … and mobile-mcp error rates" as a maintainer-facing metric, which needs the primitive's name on the telemetry path. But the value the daemon sees is req.tool out of a socket frame, and the socket is reachable by anything on the machine — so an unchecked tool is caller-supplied text wearing an enumerated field's justification. The fix is the same one verb already uses: enforce the value against a closed set at the recording site, and pin the set with a lint guard.

    'use strict';

// Structural guard, in the action-catalog / capability-catalog idiom.
//
// src/observe/event.js marks `tool` sends:true on the stated grounds that it is
// an enumerated mobile-mcp primitive name. The daemon reads that value out of a
// socket frame, and a Unix socket is reachable by anything on the machine, so
// the justification is only true if the recorded value is checked against a
// closed set first. This pins that set to the primitives DeviceBridge actually
// calls, in BOTH directions: a new bridge call that forgets the set records no
// tool name at all (silent metric loss), and a stale entry is a lie about what
// mauto does.

const fs = require('fs');
const path = require('path');

const { MOBILE_MCP_TOOLS, isKnownTool } = require('../../src/device/mobile-mcp-tools');

const BRIDGE_SRC = fs.readFileSync(
  path.join(__dirname, '..', '..', 'src', 'device', 'bridge.js'),
  'utf8'
);

// Matches the call form only — `this._call('mobile_x', …)` — so a tool name
// mentioned in a comment cannot satisfy or break the guard.
function toolsCalledByBridge() {
  const found = new Set();
  const re = /_call\(\s*'(mobile_[a-z_]+)'/g;
  let m;
  while ((m = re.exec(BRIDGE_SRC)) !== null) found.add(m[1]);
  return found;
}

describe('mobile-mcp tool allowlist', () => {
  it('knows every primitive the bridge calls', () => {
    const missing = [...toolsCalledByBridge()].filter((t) => !MOBILE_MCP_TOOLS.has(t));
    expect(missing).toEqual([]);
  });

  it('claims no primitive the bridge never calls', () => {
    const called = toolsCalledByBridge();
    const stale = [...MOBILE_MCP_TOOLS].filter((t) => !called.has(t));
    expect(stale).toEqual([]);
  });

  it('rejects anything that is not a known primitive', () => {
    expect(isKnownTool('mobile_press_button')).toBe(true);
    expect(isKnownTool('mobile_definitely_not_a_tool')).toBe(false);
    expect(isKnownTool('/Users/someone/secret-project/app.apk')).toBe(false);
    expect(isKnownTool(undefined)).toBe(false);
    expect(isKnownTool(null)).toBe(false);
    expect(isKnownTool(42)).toBe(false);
  });
});

    // preferable to failing the verb the user actually asked for.
  }

    'use strict';

// The daemon's binding of the recorder seam.
//
// Everything here exists because the daemon is a DETACHED, LONG-LIVED process
// and record() was written for a one-shot verb that records once and exits:
//
//   projectRoot  record() defaults it to process.cwd(). The daemon inherits its
//                cwd from whichever verb happened to spawn it and then OUTLIVES
//                that verb — the user can cd away or delete the directory. So
//                it is bound once, here, from MAUTO_SESSION_PROJECT_ROOT.
//   sinks        record() resolves levels per call. For the CLI that is once
//                per process; for the daemon it would be once per device call,
//                re-reading an environment that CANNOT change — nothing can
//                export a variable into a running detached process. Resolved
//                once, at construction. Consequence: MAUTO_LOG_LEVEL and
//                MAUTO_LOG_DIR are captured at spawn and pinned for the
//                daemon's lifetime; `mauto session end` is how you change them.
//   session_id   stamped on every event so one daemon lifetime is one queryable
//                group. That is the thing run_id cannot express: a daemon that
//                dies and respawns mid-run is exactly the event worth seeing.
//
// What deliberately does NOT change: the file sink still opens, appends and
// closes per event. At the default level that is ONE append per device call,
// tens of microseconds against a device round trip of 40ms or more — and a
// buffer would be unflushed at precisely the moments this exists for (the
// uncaughtException, the SIGKILL, the call that never returned).

const { record } = require('./recorder');
const { resolveLevels } = require('./settings');
const { daemonEventLogPath } = require('./paths');
const stderrSink = require('./sinks/stderr');
const fileSink = require('./sinks/file');

function daemonSinks(projectRoot, env) {
  const levels = resolveLevels(env);
  const logPath = daemonEventLogPath(projectRoot, env);
  return [
    // The daemon's stderr IS mobile-automator/.session/daemon.log (PR #176), not
    // a terminal. That inverts cli.js finish()'s calculus: a warn line here
    // costs a human no terminal noise and lands next to the adb/simctl output
    // that explains it, which is why daemon lifecycle failures are the first
    // events in this codebase that record above `info`.
    { threshold: levels.stderr, write: (e) => stderrSink.write(e) },
    { threshold: levels.file, write: (e) => fileSink.write(e, { projectRoot, env, logPath }) },
  ];
}

// Returns observe(fields) — the single function the daemon calls. Identity
// fields are applied AFTER the caller's, so no call site can forge `src` or
// claim another session's id.
function makeDaemonRecorder({ projectRoot, sessionId, env = process.env, sinks } = {}) {
  const list = sinks || daemonSinks(projectRoot, env);
  return function observe(fields = {}) {
    record({ ...fields, src: 'daemon', session_id: sessionId }, { projectRoot, env, sinks: list });
  };
}

module.exports = { daemonSinks, makeDaemonRecorder };

// Read side of mobile-automator/.session/session.json, plus the generator for
// the session id it carries.
//
// The handle is where session_id lives because it is a file that is ALREADY
// there, already written at exactly the right moment (once the daemon is
// listening) and already removed at exactly the right moment (stop()). A verb
// that wants to stamp its events with the live session's id must not have to
// pay a socket round trip for it, and a second copy in the ping reply would be
// a second source of truth that can disagree with this one.
//
// Nothing here throws: an absent, unreadable or malformed handle means "no
// session", which is a normal state, not an error.

const realFs = require('fs');
const crypto = require('crypto');

const { handlePath } = require('./session-paths');

// 16 hex chars from the CSPRNG, derived from NOTHING — not the project root,
// not the device, not the pid. That is what makes the event catalog's
// `sends: true` on session_id true rather than merely asserted, and
// tests/unit/device/session-handle.test.js is where the claim is enforced.
//
// Deliberately NOT persisted across daemon restarts. A stable id would be a
// machine fingerprint; this one changes exactly when the daemon does, which is
// the fact it exists to report — run_id cannot express "the daemon died and
// respawned mid-run".
function newSessionId() {
  return crypto.randomBytes(8).toString('hex');
}

function readHandle(projectRoot, { fs = realFs } = {}) {
  try {
    const parsed = JSON.parse(fs.readFileSync(handlePath(projectRoot), 'utf8'));
    return parsed && typeof parsed === 'object' ? parsed : null;
  } catch (_) {
    return null;
  }
}

function readSessionId(projectRoot, { fs = realFs } = {}) {
  const handle = readHandle(projectRoot, { fs });
  const id = handle && handle.session_id;
  return typeof id === 'string' && id ? id : null;
}
