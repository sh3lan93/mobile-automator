    Versions renumbered 2026-10-27: v0.37.0 shipped the same morning (PR #270, which also moved the workspace directory to .mobile-automator/). Ladder now: S0a 0.37.1 · S0b 0.38.0 (BREAKING) · S0c 0.38.1 · R1–R7 0.39.0-rc.0…rc.7 · G 0.39.0. Wherever this file says mobile-automator/<x> for the workspace, read .mobile-automator/<x>.

    Context¶

    The 2026-10-26 gap analysis (42 items on GitHub Project #4) traced most enterprise, DX and promotion blockers to one locked decision in PRD #69: the agent owns the execute loop, so every replay needs an LLM issuing 4–6 verbs per step. Verified by hand on v0.36.1: no run verb; the FAQ CI recipe never executes a test; result finalize --status failed and failed assert exit 0; validate passes duplicate ids, target-less taps and dangling after_step; finalize reports passed for a nonexistent scenario with zero assertions; 12/27 assertion types are agent-judged with no provenance; no JUnit.

    The repo already holds an agent-free executor: sample-app/scripts/lib/executor.js + resolve.js (unit-tested, drives the real-device E2E). Measured on the 12 repo example scenarios: 100% of steps executable without an agent, 87% of assertions mechanical today, 42% of scenarios fully agent-free; reference screenshots and five element-list promotions push that to ~100% / ~75%+.

    Intended outcome: mauto run <scenario> replays a scenario in-process, deterministically, with meaningful exit codes, JUnit output, provenance in the result file, and reference-screenshot assertions; the agent only handles what the runner marks needs_agent. Landed as one PRD, slice by slice, with no partially-visible state on main.

    Routine choices made here: gate env var MAUTO_REPLAY=1 (avoids the MAUTO_RUN_ID prefix); feature vocabulary "replay" / "reference screenshots" (never "golden": sample-app/scenarios/golden/ already means normalized result fixtures); variable substitution syntax ${name} (no collision with the {{placeholder}} guide guard); undecided assertions persisted as status: "needs_agent" with upsert-on-rerecord; a failed or incomplete run is ok:false with the full summary in data (the partial precedent; the harness shim treats ok:true + non-zero as a bug).

    Current status (verified; details in Appendix)¶

    • Executor exists but is harness-only. executor.js covers launch (cold→--resume via catalog.stepFlagsFor), wait_for_element, tap, type, 4 semantic presses, retry_policy, checkpoint/failure screenshots, mechanical assertions, result add-step/add-assertion/finalize, stop at first failed step. Missing: condition, optional, on_failure skip, sub_steps, capture_value/variables, scroll_to_element, wait_for_element_gone, wait_for_loading_complete, long_press, double_tap, swipe, press_button, open_url, preconditions. Tier-2 assertions are recorded as failures. It spawns a subprocess per verb; src/ may not require child_process (telemetry-transport-isolation guard) → the shipped runner must be in-process.
    • The seam for in-process execution exists. withBridge(device, fn) (cli.js:1955) keeps one DeviceBridge open for any number of calls, then probes crashes, captures failure screenshots, emits, closes. The daemon caps a single call at 25 s and idles after 5 min of silence; a polling loop never trips either.
    • Result layer is additive-friendly but thin. addAssertion drops type/step_id; status enums are closed (passed|failed); required lists are frozen by result-schema-additive.test.js; everything else tolerates new optional fields. finalize derives status from assertion counts only.
    • Invariant wording blocks the verb, not its substance. CLAUDE.md:144 "No interactive run co-routine" (PRD #69: "no interactive co-routine — one-shot shell is the portable primitive"). A batch run <file> that exits with one envelope is a one-shot verb; the session daemon was accepted on the same reasoning (CHANGELOG v0.11).
    • Guards that will fire (all handled in-slice): vocab-drift (VERB_NAMES), envelope EXIT exact-equality test, assertion-split-docs + docs-counts, replay-warnings-boundary + docs-replay-warnings, result-coverage, config-schema, e2e-agnostic file-location rules, the execute-guide anchor guards, no-observe-gate pattern (clone for the new gate at graduation).
    • Baseline: main @ b4f36a9, v0.36.1, 2582 tests / 153 suites green, lint and audit clean.

    Goal (target state at graduation)¶

    • mauto run <scenario> [--device] [--run-id] [--junit <path>] [--update-references] [--timeout-ms] [--judge none] — one invocation, one envelope. Exit 0 passed, 6 test_failed, 7 incomplete (something needs the agent), 2/3/5 as today. data = {run_id, scenario_id, status, result_path, duration_seconds, steps{…}, assertions{total,passed,failed,needs_agent}, failed_step, pending[], junit_path, executor}; the incomplete hint carries the exact mauto result add-assertion … --judge agent commands.
    • Coverage: 20/23 actions executed in-process (3 unsupported → step needs_agent); 15 element-list + 5 promoted + screenshot_match = 21/27 assertion types decided without an agent; remaining 6 → needs_agent with provenance.
    • result finalize --status failed and failed assert exit 6; result export --format junit; validate enforces references (unique ids, after_step, targets, declared variables); every result carries executor provenance and per-assertion judge.
    • Execute guide: "run mauto run, then handle needs_agent"; the manual per-step recipe survives as the fallback section. The real-device E2E harness is a thin caller of mauto run, so the runner is what CI proves on both engines.
    • Invariant amended; gate removed; tests/lint/no-replay-gate.test.js forbids MAUTO_REPLAY.

    run handler shape (cli.js)¶

    program.command('run <scenario>', { hidden: true })   // hidden until graduation
  .action(withEnvelope(requireWorkspace((file, opts) => {
    const refusal = gateRefusal(process.env);          // fail('environment', …, 'export MAUTO_REPLAY=1')
    const pre = prepareRun({validator, projectRoot, file, opts}); // read + schema + referential → invalid_input before any device work
    emitters.setRunId(pre.runId);                      // so device events land in run-<id>.ndjson and measureRun sees them
    return withBridge(opts.device, bridge => handleRun({bridge, resultStoreFactory, memoryStoreFactory, projectRoot, config}, pre, opts));
  })));
    handleRun → ok(data) / fail('test_failed', …, data) / fail('incomplete', …, data); shares a finalizeRun() helper extracted from handleResultFinalize (measureRun, store.finalize, pruneRunTraces, memory recordRun). Gate is on behaviour, registration is unconditional (vocab-drift builds the program in a plain env).
