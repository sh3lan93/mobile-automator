# Drift guards (tests/lint)

Nested guide for `tests/lint/`; split out of the root CLAUDE.md so it loads only when working here. Read before touching actions or result fields.

Two catalogs are the single source of truth for "does this capability actually reach the device / the result file". Both are consumed by lint tests, so a capability that loses its CLI reach **fails the build** instead of silently degrading.

**`src/device/action-catalog.js`** (#117) binds every scenario-schema action to *how* it executes, via a `resolution` field. Guard: `tests/lint/action-coverage.test.js`.

| resolution | meaning |
|---|---|
| `verb` | dedicated one-shot `mauto` verb → DeviceBridge → one or more mobile-mcp primitives (`launch` is terminate + launch, #255) |
| `semantic` | invoked as `mauto press <action>`, resolved per-platform by `src/device/semantic-press/` |
| `composed` | no verb; the agent composes it from existing verbs (the execute guide documents how) |
| `unsupported` | no `mauto` verb reaches it (`clear_app_data`: mobile-mcp 1.0.15 added the primitive, mauto has not wired it; `enable_wifi`, `disable_wifi`: mobile-mcp has no primitive) — guides must **not** promise a verb |

**`tests/integration/mobile-mcp-contract.test.js`** (#199) is the engine-side counterpart of `tests/lint/mobile-mcp-tool-coverage.test.js`. That lint guard pins our tool-name list to what `bridge.js` calls — both sides are our code, so it cannot see the engine move. The contract test spawns the pinned mobile-mcp, sends only `listTools` (no device needed), and fails when a tool we call disappears, a key we send is no longer accepted, or a newly required key appears that we do not send. The keys are derived by driving every `DeviceBridge` method through production's `makeCall`, not hand-restated. It exists because mobile-mcp's argument schemas are non-strict: an unknown key is dropped and the call still reports success — `bridge.screenshot` once sent `path` instead of `saveTo`, and every screenshot was a silent no-op.

**`src/result/capability-catalog.js`** (#140) binds every fact a result file can carry to the result schema, the `ResultStore` method that writes it, and the `mauto result` flag that supplies it. Guard: `tests/lint/result-coverage.test.js`. This exists because `assertion_results` silently stayed empty for months — the schema had a home for it and no verb could fill it.

**`package.json` `engines.node`** (#162) is the single source of truth for the supported Node range, and must stay a bare `>=X.Y.Z` floor — the guard rejects a compound range like `^20 || ^22` outright, because there is no single floor to check prose against. Guard: `tests/lint/node-version-agreement.test.js` — derives the floor and fails when the README badge, any prose claim in a shipping doc, `test.yml`'s matrix, or any workflow's literal `node-version` disagrees. It matches *any* Node-adjacent major rather than an enumerated list of phrasings, so a newly-written claim is caught by default; the rare sentence that names a Node version without claiming support goes in `NOT_A_CLAIM`.

**`package.json` `os`** (#165) is the single source of truth for which host OSes run mauto (`darwin`, `linux`) — npm enforces it at install (`EBADPLATFORM`), and `src/device/host-support.js` derives `SUPPORTED_HOSTS` from it to fail device/session verbs on anything that slips past (`--force`, `npm link`). Guard: `tests/lint/host-support-agreement.test.js` — fails when `os` is empty or claims `win32`, when `SUPPORTED_HOSTS` disagrees with it, when `README.md` or `docs/getting-started/installation.md` fails to name every host (via a map keyed on `os`, so a new host forces a doc update) plus Windows/WSL2, or when `TROUBLESHOOTING.md` loses the heading the runtime hint cites.

**`package-lock.json`** must mirror `package.json`'s `name`, `version`, `engines.node` and `os`. Guard: `tests/lint/lockfile-in-sync.test.js`. CI installs with `npm ci`, which installs *from the lockfile*, so a stale root entry is invisible until something downstream reads the wrong value — it has drifted twice.

**`LICENSE`** (#160) must be the verbatim Apache-2.0 text from apache.org — it shipped a 644-byte stub for months. Guard: `tests/lint/license-full-text.test.js` restores the appendix copyright line to its `[yyyy] [name of copyright owner]` template and compares the SHA-256 against the canonical file, so the copyright line is the only line that may differ. To change the text, re-fetch it rather than re-pin the hash.

**Production-dependency advisories** (#161) are gated by `scripts/audit-gate.js`, which runs `npm audit --omit=dev` and fails on any high/critical advisory not listed in `scripts/audit-allowlist.json`. Every allowlist entry carries a reason, the issue that removes it, and an `expires` date. An expired entry fails, and so does a *stale* one (its advisory is no longer reported), so accepted risk can't outlive its reason. It runs in `audit.yml` (PR, main, weekly — a signal) and in `release.yml`'s `publish-npm` before `npm publish` (the actual gate). Wiring guard: `tests/lint/supply-chain-gate.test.js`. Dependabot is `lockfile-only` on purpose: a `package.json` change would trip the version-bump gate, and users resolve our ranges fresh anyway.

**ESLint** (#164) runs `npm run lint` (`eslint.config.js`) in `lint.yml` (PR, main — a required check since #249) and in `release.yml`'s `publish-npm` before `npm publish` (the actual gate). Its point is the type-aware block over `src/`, `bin/` and `scripts/`: `no-floating-promises` and `no-misused-promises` catch the async callback whose rejection nobody observes — on its first run it found the session daemon exiting on a `null` frame. Guard: `tests/lint/eslint-gate.test.js` pins the script, both rules at `error`, and both CI runs. Those rules need TypeScript's types, and TS 6 no longer auto-loads `@types/*`, so the `@types/node` devDependency plus `"types": ["node"]` in `tsconfig.eslint.json` are load-bearing: without them every Node API is untyped, and the rules silently report nothing (they missed the daemon bug that way). It lives in its own workflow because `node-version-agreement.test.js` requires every `test.yml` job to run the Node matrix.

**`release.yml`'s job order** (#186) is the release gate, because the required PR checks prove the PR, not the tag `auto-tag.yml` pushes (see [Releasing & version handling](../../.github/CLAUDE.md)). Guard: `tests/lint/release-gate.test.js` — fails when the `verify` job's Node matrix stops deep-equalling *every* `test.yml` job's (read from `test.yml`, never restated, so the floor is covered transitively by the Node guard above — and test.yml's own two restatements, `test` and `pack-smoke`, are pinned to each other by the same sweep), when `verify` stops running the same suite command `test.yml`'s test job runs (`npm run test:all`) plus `./scripts/pack-smoke.sh` on `${{ matrix.node-version }}` with `fail-fast: false`, when `verify` stops needing `resolve` (the needs line is what keeps a rejected manual ref from reaching the release job with an empty tag), when an `if:` or `continue-on-error` neutralises any of it, when `publish-npm` stops needing `verify`, when `publish-npm`'s `if` stops being exactly the rc guard (the `|| skipped` clause in the `release` job's `if` is only sound while that guard is the one thing that can skip publish), or when the `release` job's `needs` or its exact `if:` changes.

**The version gate** (#369) is `scripts/version-gate.js`: a `package.json` version must be untagged and greater than the highest release tag, ordered by `scripts/version-order.js` (the one SemVer comparison; its `highestRelease()` finds the highest tag for both the gate's `decide()` and `scripts/sync-branch.js`, which picks a free version by the same rule over the gate's `gitTags()`). The old check asked only whether `v<version>` existed, so 0.40.13 merged after v0.40.14 shipped. It runs in `version-check.yml` (`--mode pr`) and again in `auto-tag.yml` (`--mode tag`, step `tag_check`) before the tag push, since a stale branch can merge on an old PR run. Tag mode skips a `tagged` version only when `SHIPPING_PATHS` (`src`, `bin`, `package.json`) are unchanged since `v<version>`; otherwise it fails, since a stale branch reused a released version. Guard: `tests/lint/version-gate.test.js` — fails when either call is removed or changes mode, when the tag-mode step stops being `tag_check` or moves after `git push origin`, when tags are not fetched first, when an `if:` or `continue-on-error` neutralises a gate step (or `create-tag`), when a checkout loses `fetch-depth: 0`, or when `SHIPPING_PATHS` stops equalling the `cli` paths-filter list in `version-check.yml`; it also drives `decide()` through the issue's cases (`0.40.13` vs `v0.40.14`, `0.40.10` vs `v0.40.9`, `-rc.N` vs its release both ways).

**`.github/required-checks.json`** (#249) is the whole `main-branch` ruleset policy — `repo`, `ruleset_id`, `enforcement`, `integration_id`, `strict`, `required_approving_review_count`, `bypass_actors` and the required `checks` — and the ruleset itself, which lives outside git, is applied from it by `scripts/apply-ruleset.js` (dry run by default; see [Releasing & version handling](../../.github/CLAUDE.md)). The script's transform is unit-tested in `tests/unit/apply-ruleset.test.js`, and the guard reads the file through the script's own `loadPolicy`, so both share one parser. Guard: `tests/lint/required-checks.test.js` — fails when a listed name is produced by zero or more than one workflow job (job `name`s are expanded over their matrix, so the `test` job yields one `Test (…)` name per entry in its `node-version` matrix; a renamed job or a changed matrix fails here instead of leaving a check that never reports and blocks every PR forever), when the producing workflow's `pull_request` trigger has a `paths`/`paths-ignore` filter (no run means no check run, so the check stays pending forever — unlike a job-level `if:` skip, which counts as success), when a job a required job `needs` is not itself required (a failed needed job *skips* its dependent, and a skipped check satisfies a required one — why `Detect CLI code changes` sits next to `Verify version is bumped`), or when the producing job is neutralised: a job-level `if:` other than the one pinned in `ALLOWED_JOB_IFS` (`version-check.yml#check-version`'s, exact expression), any step `if:`, or `continue-on-error` on the job or any step. Only workflows with a `pull_request` trigger are searched for producers, so a tag-only workflow's matrix cannot break it.

**`tests/lint/workflow-guard.js`** is the shared helper module for the workflow-parsing guards (`supply-chain-gate`, `eslint-gate`, `release-gate`, `required-checks`, `version-gate`, `docs-ci-recipe`, `showcase-replay-workflow`): `loadWorkflow`, `runs`, `executedScripts` (every step's `run:` plus an action's `with.script`, the emulator runner's commands), `isAlways` (an `if:` that is exactly `always()`, bare or in `${{ }}`; pinned with `executedScripts` in `docs-ci-recipe`'s helper tests, since both guards only feed them compliant workflows), `findStep`, `findJobWithRun`, `findProducer` (the one job reporting a check name; throws naming every producer unless there is exactly one), `asList`, `expandJobNames` (a job's check-run names, matrix-expanded; throws on anything GitHub would compute rather than the YAML spell out). It is to those guards what `tests/lint/docs-corpus.js` is to the prose guards — #161, #164 and #186 had each grown a private copy of the same helpers, one rename apart, and three hand-maintained copies is the drift threshold #162's corpus extraction already taught us. The next wiring guard consumes this module; it does not grow another private copy.

**Schema validity** (#191): every `src/schemas/*.json` must be valid Draft-07, compile under Ajv strict mode (which catches misspelled keywords like `"requird"` that `strict: false` silently accepts), and compile with the CLI's own Ajv — `createCliAjv()` from `src/schemas/cli-ajv.js`, the single construction site; the guard imports the factory rather than mirroring its options, and fails on any other `new Ajv(` in `src/` or `bin/`, so the options cannot drift back into hand-copied literals. Guard: `tests/lint/schemas-valid.test.js`. It replaced the path-filtered `validate-schemas.yml` workflow, which installed `ajv` outside the lockfile.

**The shipping-doc corpus** is `tests/lint/docs-corpus.js`: every tracked `.md` minus historical records (`CHANGELOG.md`, `docs/changelog.md`, `docs/plans/**`), enumerated with `git ls-files` so `.gitignore` never has to be restated. Four guards scan it — `docs-counts.test.js` (capability counts vs the schema), `docs-no-stale-extension.test.js` (the removed Gemini-extension model), the Node guard above, and the unsupported-action rule below. A new doc-scanning guard consumes `shippingDocs()`; do not hand-maintain a second file list, which is how `sample-app/README.md` kept teaching removed slash-command syntax for months.

**The real-device E2E** (#94) is `sample-app/scripts/run-e2e.mjs`, run by `sample-app-e2e-android.yml` on an API 36 emulator (not 33: there even the legacy engine cannot recover TextField labels, #251). It drives the **shipped** `mauto` binary (`MAUTO_BIN`; in CI the packed tarball) with one `mauto run <file> --run-id <id> --junit <path>` per scenario, accepting `test_failed` and `incomplete` as answers, and classifies off the run data in that envelope — the frozen contract a CI job reads (`src/run/summary.js`; `incomplete` is not a pass) — while the result file it wrote feeds the golden comparison; a run that answers without its JUnit report is a harness error, and the reports land in the artifacts. Since replay R7 (#283) the harness executes no step and resolves no target, so CI proves the shipped runner on both engines — never a private MCP client, engine pin, executor or matcher, which is what earlier harnesses had. `sample-app/scenarios/golden/known-failures.json` excuses a scenario only when its first failed step is the entry's `failing_step` (XFAIL); failing elsewhere is FAIL and passing is XPASS, both job failures. Guard: `tests/lint/e2e-agnostic.test.js` — no OS element-id tokens in the harness, `run-e2e.mjs` calls `mauto run` through the shim (`.run(['run', …])` with both accepted kinds and no opt-in gate variable is `tests/lint/retired-gates.test.js`'s rule), no `lib/executor.js` or `lib/resolve.js`, no harness file naming `findFirst`, `matches(` or `resolveTarget` or requiring the evaluator, action catalog or field mapping, no own matcher, no scenario target equal to an app Semantics id, no `sample-app/scripts/package.json`, every known failure pinned to an issue, reason and existing step, and the golden gate keyed on the scenario's `golden` tag (`sample-app/scripts/lib/golden.js`, loud in both directions), never a `golden_` id prefix.

**The showcase app's scenarios** (#305, PRD #304) are `showcase-app/scenarios/*.json`, one file per flow for both platforms. Guard: `tests/lint/showcase-scenarios.test.js` — fails when the directory holds no scenario, when a scenario fails `mauto validate --strict` (checked through the CLI's own `loadScenario` in `src/scenario/load.js`, never by recombining the validator and replay warnings), is not schema `2.1` / `platform-agnostic` / `cross-platform`, uses an assertion type outside `MECHANICAL_TYPES`, names an OS element id anywhere in its text, or launches an `app_package` other than the Android `applicationId` and the iOS `PRODUCT_BUNDLE_IDENTIFIER` resolved from `project.pbxproj` with `Config.xcconfig`'s values (every build configuration must resolve to the same id, and it must equal the `applicationId`); when a scenario target or expected value equals a `testTag("…")` literal in the app source; when a step target, or an assertion target or expected value, positioned after a `type` step (assertions by `after_step`) would match text typed earlier by the CLI's own `matches` (`src/assertion/evaluator.js`, not a copy), or a step `target_pattern` or assertion `pattern` there matches it, because the CLI resolves targets and patterns against element text and Android exposes a field's typed text while iOS does not; or when any showcase Gradle file or version catalog names a UI test dependency (Espresso, `androidx.test`, Compose `ui-test`, XCUITest) or an `androidTest` / `androidInstrumentedTest` / `*UITests` directory exists; or when any `.kt` file under `showcase-app/shared/src/commonMain` other than `screens/common/BackTopBar.kt` names `ArrowBack`, or when `BackTopBar.kt` itself no longer does, so the back-arrow top bar is never copied again (#311). The OS-id regex and the step/assertion target walk (each value with the step it is anchored to, steps via `flattenSteps` so `sub_steps` count, an unresolvable anchor reported) live in `tests/lint/scenario-targets.js`, shared with `e2e-agnostic.test.js`; a third scenario guard imports them rather than growing a copy.

**Retired feature gates** (#284): a multi-PR feature ships behind an opt-in environment variable and its graduation PR deletes it (observability in v0.26.0, replay / `mauto run` in v0.40.0). Guard: `tests/lint/retired-gates.test.js` — one row per retired gate (its variable name and the files that implemented it); fails when a name appears in any file git knows outside the historical records (`CHANGELOG.md`, `docs/changelog.md`, `docs/plans/**`), workflows included, or when a listed file comes back. The file list is `repoFiles()` from `tests/lint/docs-corpus.js`, never a hand-kept list of roots. Graduating the next feature adds a row, not another guard file.

**The `mauto run` contract in the docs**: `tests/lint/docs-run-contract.test.js` pins the `mauto run` row of `docs/reference/cli-verbs.md` to `RUN_DATA_KEYS` (`src/run/summary.js`) and `EXIT` (`src/output/envelope.js`); `tests/unit/guide/execute-content.test.js` pins both execute guides the same way, and the `mauto bootstrap` line is built from `EXIT`.

**CI recipes in the docs** (#277): the FAQ's CI recipe once stopped at a comment where the test run belonged, and its GitHub Actions example pinned `@v3` actions and executed nothing. Guard: `tests/lint/docs-ci-recipe.test.js` — over the shipping-doc corpus, every `uses: <action>@<ref>` in a fenced block must pin a ref this repo's own workflows use for that action (read from `.github/workflows/`, never restated, so bumping a workflow action fails the build until the docs follow); both FAQ CI answers must run `mauto run … --junit` in a fenced block, and the Actions example must upload with `if: always()`; no shipping doc may name the "latest" result file the old recipe read, which mauto never writes (results are `<run_id>.json`).

**The showcase replay workflow** (#313, PRD #304) is `.github/workflows/showcase-replay.yml`: weekly and `workflow_dispatch` only, it replays every showcase scenario with `mauto run` (through the generic `showcase-app/ci/replay.sh`, against the device id the generic `showcase-app/ci/device-id.sh` reads from `mauto devices`) on an API 36 emulator and an iOS simulator against live TMDB, after the app-specific `showcase-app/ci/tmdb-check.sh` has ruled out an outage or data drift. Nothing runs it on a PR, and it is the file people copy, so its wiring is pinned. Guard: `tests/lint/showcase-replay-workflow.test.js` (through `workflow-guard.js`'s `loadWorkflow`) — fails when the triggers are anything but `schedule` (`23 4 * * 1`) + `workflow_dispatch`, except a `push` limited to `sample-app/313-ci-workflow` while the file carries `TEMPORARY(#313)` (the pre-merge run; `workflow_dispatch` only exists for files on the default branch), or name `pull_request` / `pull_request_target`; when a job name is in `.github/required-checks.json`; when `secrets.TMDB_API_KEY` appears anywhere but as an `env:` value, or a `run:` / emulator `script:` names `secrets.` or echoes, prints or cats a variable bound to it; when `tmdb`, `android` or `ios` stops needing `key` and gating on `needs.key.outputs.has_key` (so forks skip green), or a device job stops needing `tmdb` (so an outage never reads as a red replay); when either device job stops calling `ci/replay.sh` with an unquoted `$SCENARIOS`, or the top-level `SCENARIOS` glob (relative to `APP_DIR`) stops resolving to exactly the files in `showcase-app/scenarios/`; when `replay.sh`'s `"$mauto" run` line loses `--device` or `--junit`, or its `case` labels for `passed`, `failed` and `needs_agent` stop equalling `EXIT.OK`, `EXIT.TEST_FAILED` and `EXIT.INCOMPLETE` (`src/output/envelope.js`), or the exit codes its retry skips stop being exactly `EXIT.OK` and `EXIT.INCOMPLETE`; when a device job stops calling `ci/device-id.sh` with its own platform, or any workflow script runs `jq` over `mauto devices` output; when a device job's `upload-artifact` step loses `if: always()`; when the discover parameter names `tmdb-check.sh` sends stop equalling the `put("…")` keys of `FilterState.toDiscoverQuery()`, any of its `search/movie` calls stops sending exactly the `parameter("…")` names of `KtorTmdbClient.searchMovies`, or its `MIN_VOTES_FOR_RATING` stops equalling the Kotlin constant (the script is a deliberate second copy of both queries); when an annotation title (`::error|warning|notice title=…::`, or `replay.sh`'s `title="…"`) in the workflow or its three `ci/` scripts contains a comma, since GitHub splits workflow-command properties on `,`; when a step named `(generic)` names `tmdb` (any case, so `ci/tmdb-check.sh` too) in its `run:`, `with.script` or `env:` (an env entry that only passes a secret through, `KEY: ${{ secrets.X }}`, is exempt, since secrets stay step-scoped), or sets `REPLAY_PROBE`, or the top-level `env:` stops defining `REPLAY_PROBE`, so the app-specific probe stays in the per-app block a copy edits; when the Android emulator step stops setting a device `profile` (the default AVD is 320x640, where the app's top bar hides the "Popular films" title every scenario waits for); or when mauto stops installing from npm at `MAUTO_VERSION`, or a device job packs a tarball.

**The long-press default duration** (#324) is `DEFAULT_LONG_PRESS_MS` in `src/device/bridge.js`; `mauto long-press --help` derives its text from it, and the guides deliberately do not state it (an agent reads the value used from `data.duration`). Guard: `tests/lint/long-press-default-docs.test.js` — over the shipping-doc corpus, every long-press line claiming a default (`defaults to N ms`, `default N`, `presses for N ms`) must name the constant's value, and at least one doc must make the claim, so a rewording cannot leave it checking nothing.

**Docs vs unsupported actions** (#166): a rule in `tests/lint/action-coverage.test.js` scans the shipping-doc corpus and fails when a line names an `unsupported` action (`clear_app_data`, `enable_wifi`, `disable_wifi`) without also saying it is unsupported. **Assertion split**: `tests/lint/assertion-split-docs.test.js` pins `MECHANICAL_TYPES` and `REFERENCE_SCREENSHOT_TYPES` to the three-way (mechanical / reference screenshot / agent) table in `docs/reference/assertions.md`, so a new assertion type must be placed in exactly one class.


## Schemas and `validate`

- Scenario: `src/schemas/scenario_schema.json` (`$schema_version` `"2.0"` or `"2.1"`; enums for step actions, precondition device actions and assertion types, named string IDs, root-level `variables`/`preconditions`). Print with `mauto schema scenario`; validate a file with `mauto validate <file>`. Note: `validate` still accepts actions the action-catalog marks `unsupported` (schema compatibility) but reports each as a `data.warnings[]` entry with `code: 'unsupported_action'`; `--strict` turns them into `invalid_input`. A lint guard in `tests/lint/action-coverage.test.js` fails the build if a shipping doc presents one as working (#166).
